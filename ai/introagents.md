## 1. LLM

**LLM** (Large Language Model, велика мовна модель) - це нейронна модель, яка отримує на вході контекст і на його основі генерує відповідь. Але безпосередньо з текстом модель не працює — текст спочатку перетворюється на токени.

**Токен** — це елементарний фрагмент тексту, з яким працює мовна модель. Токеном може бути ціле слово, частина слова, знак пунктуації або інший фрагмент тексту. Наприклад, умовно:

```
"Модель генерує відповідь"
```

після токенізації може виглядати приблизно так:

```
["Модель", " генеру", "є", " відповідь"]
```

Але для моделі ці токени представлені числовими ідентифікаторами, наприклад:

```
[15342, 2871, 418, 32654]
```

Тобто текст проходить приблизно такий шлях:

```
текст → фрагменти тексту → ID токенів → числові вектори → LLM
```

Сам `15342` тут нічого не означає як число — це просто номер певного токена у словнику токенізатора. Перед обробкою моделлю цей ID перетворюється на числовий вектор (embedding).

Сама відповідь при цьому генерується послідовно. Спочатку LLM обробляє весь переданий їй контекст — це можуть бути десятки або навіть сотні тисяч токенів — і генерує наступний токен. Цей токен додається до вже наявного контексту, після чого генерується наступний, і так далі.

Щоб під час генерації відповіді кожного разу не перераховувати весь попередній контекст заново, зберігається його вже обчислений стан — так званий KV-cache. Тому після початкової обробки великого контексту генерація йде по одному новому токену за крок.

Але коли користувач надсилає наступне повідомлення, це вже нове звернення до LLM. Система знову формує актуальний контекст, у який може увійти попередня розмова разом із новим повідомленням, і запускає новий цикл обчислень моделі. Технічно частина попередніх обчислень також може кешуватися і повторно використовуватися, але принципово це новий запуск LLM, а не продовження роботи нейронної мережі, яка весь цей час зберігала стан розмови.

Тобто між моїми повідомленнями LLM не сидить у якомусь стані й не «пам'ятає», про що ми говорили. Її поведінка при наступному зверненні визначається тим, який контекст система знову подасть їй на вхід.

### Чому довгі відповіді можуть втрачати точність

LLM генерує відповідь послідовно, токен за токеном. Кожен згенерований токен додається до контексту, тому при генерації наступного модель спирається вже не тільки на початковий запит, а й на власну попередню відповідь.

Через це в довгій відповіді можуть накопичуватися невеликі помилки та припущення. Якщо модель десь на початку пішла не зовсім правильною логікою, написане нею саме стає частиною контексту, і далі вона може цілком послідовно розвивати вже неправильну гілку. Крім того, зі збільшенням контексту окремі деталі початкового запиту можуть враховуватися гірше.

KV-cache дозволяє не перераховувати весь попередній контекст для кожного нового токена, але сам по собі не є причиною втрати точності — це лише оптимізація обчислень. 

Тобто спрощено:

```
довга генерація → власний текст стає частиною контексту → можливе накопичення відхилень і помилок
```

Це також пояснює, чому іноді краще зупинити невдалу довгу відповідь, уточнити умову і зробити новий запит, ніж чекати, що модель сама повернеться до правильної логіки.

Так. Перед переходом до ChatGPT я б додав ще одну коротку річ — що LLM сама по собі нічого не «пам'ятає» між окремими зверненнями. Це якраз створить природний місток до ChatGPT.

### Що LLM пам'ятає між запитами

Сама LLM не зберігає нашу розмову як свою внутрішню пам'ять. Кожне нове звернення — це новий запуск обчислень моделі з тим контекстом, який їй цього разу передали. Тобто модель сама по собі не знає, про що ми говорили хвилину тому. Щоб вона могла продовжити розмову, хтось повинен зберегти попередній діалог і знову передати потрібну його частину моделі.

Спрощено:

```
LLM: контекст → обчислення → відповідь
```

А збереження історії, формування нового контексту, робота з файлами, пам'яттю та інструментами — це вже робота програмної системи навколо LLM.S

## 2. ChatGPT

ChatGPT — це вже не просто LLM, а програмна система, побудована навколо неї. Якщо сама LLM фактично працює за принципом:

```text
контекст → LLM → відповідь
```

то одна з основних задач ChatGPT - сформувати для неї правильний контекст. Саме ChatGPT організовує історію розмови, пам'ять, роботу з файлами, системні інструкції та результати роботи інструментів і вирішує, яку з цієї інформації передати LLM при черговому зверненні.

Тобто спрощено:

```text
історія + пам'ять + файли + інструменти + поточний запит
                         ↓
               формування контексту
                         ↓
                        LLM
                         ↓
                     відповідь
```

При цьому:

```text
інформація десь збережена ≠ інформація зараз у контексті LLM
```

Наприклад, те, що ми щось обговорювали раніше або завантажили PDF у проєкт, ще не означає, що весь цей текст зараз переданий моделі. ChatGPT повинен вибрати потрібну інформацію і включити її в поточний контекст.

Крім керування контекстом, ChatGPT дає LLM можливість користуватися інструментами: шукати інформацію в Інтернеті, виконувати код, працювати з файлами та зовнішніми сервісами. Результат роботи такого інструмента знову може бути доданий до контексту і переданий LLM.

```text
ChatGPT = LLM + керування контекстом + пам'ять/історія + інструменти + інтерфейс
```

### Файли

LLM безпосередньо не працює з PDF, DOCX чи іншими форматами файлів. Щоб використати їхній вміст, ChatGPT спочатку повинен його обробити і отримати представлення, з яким можна працювати далі. Для великих документів це може виглядати приблизно так:

```text
PDF → обробка → текст/структура → фрагменти → індекс
                                           ↓
                                  пошук потрібного
                                           ↓
                                       контекст
                                           ↓
                                          LLM
```

Тобто якщо я завантажив книгу на 500 сторінок, немає потреби передавати всі 500 сторінок LLM при кожному моєму запиті. Система може знайти фрагменти, які стосуються конкретного питання, і передати моделі тільки їх.

При цьому сам PDF може залишатися як оригінальне джерело. Якщо з документом треба багато працювати, текстовий формат, наприклад Markdown, може бути зручнішим як робоче представлення, але це не означає, що всі PDF треба попередньо перетворювати в Markdown.

І тут добре видно вже знайомий принцип:

```text
файл збережений → інформація доступна ChatGPT

фрагмент файла потрапив у контекст → інформація доступна LLM зараз
```

### Історія і пам'ять

З історією розмови ситуація схожа. Те, що весь чат збережений і я можу його прокрутити назад, не означає, що вся ця історія кожного разу передається LLM.

ChatGPT може використовувати частину попередньої розмови, стислий виклад або іншим способом вибирати інформацію, потрібну для формування поточного контексту.

Окремо є пам'ять — інформація, яку система може зберігати між розмовами і використовувати пізніше. Але й вона не є «пам'яттю всередині LLM». Це ще одне зовнішнє джерело інформації, з якого ChatGPT може щось додати до контексту.

Тому я б для себе розділив це так:

```text
історія — що було в попередній розмові
файли   — збережені зовнішні матеріали
пам'ять — окремо збережена інформація для подальшого використання
контекст — що з усього цього LLM фактично бачить зараз
```

Остання схема, як на мене, тут найцінніша. Вона прибирає плутанину між «ChatGPT має доступ до інформації» і «LLM зараз працює з цією інформацією».

Я б виділив це як завершальний підпункт розділу про ChatGPT — він одночасно підсумовує і готує перехід.

### Промпт і системні інструкції

**Промпт** — це інструкція або запит, який передається LLM і впливає на те, яку відповідь вона повинна сформувати. Коли я пишу повідомлення в ChatGPT, це фактично мій користувацький промпт.

Але мій промпт — не єдина інструкція, яку отримує модель. Програмна система може передати їй ще й системні інструкції. Вони задають загальні правила її поведінки: роль, стиль роботи, обмеження, доступні інструменти, порядок їх використання тощо.

**Системні інструкції** — це спеціальна частина вхідного контексту, якій модель навчена надавати вищий пріоритет порівняно з інструкціями користувача. Вони задають загальні правила поведінки моделі, її роль, обмеження та правила використання інструментів. Тобто різниця між системною інструкцією і звичайним промптом існує не тільки на рівні ChatGPT — сама модель навчена розрізняти їхні ролі та пріоритети.

Спрощено:

```
системні інструкції
+ історія та пам'ять
+ інформація з файлів
+ результати інструментів
+ мій промпт
= контекст для LLM
```

Наприклад, ту саму LLM можна системною інструкцією налаштувати на різну поведінку:

```
"Ти помічник програміста..."
"Ти аналізуєш документи..."
"Відповідай коротко і тільки українською..."
"Для виконання задачі можеш використовувати такі інструменти..."
```

Тобто модель при цьому може залишатися тією самою — змінюється те, що їй сказали робити і в яких умовах вона повинна працювати.

Це важливий момент для подальшої розмови про агентів: **спеціалізацію можна отримати не тільки навчанням або зміною самої моделі, а й системними інструкціями, доступними інструментами та контекстом.**

До речі, тут я б обережно використовував слово «промпт». У широкому побутовому сенсі ним часто називають взагалі весь текст, який подається моделі. Але в нашому поясненні краще розділяти `користувацький промпт`, `системні інструкції` і весь `контекст`. Це потім зменшить плутанину з агентами.

### Що в результаті робить ChatGPT

Отже, для себе я виділив три основні речі:

1. LLM — це не ChatGPT. LLM виконує основну «інтелектуальну» роботу, але ChatGPT — це програмна система, побудована навколо неї.
2. Одна з ключових функцій ChatGPT — керування контекстом. Історія розмови, пам'ять, файли, системні інструкції та результати роботи інструментів є джерелами інформації, з яких формується те, що LLM «бачить» при конкретному зверненні.
3. ChatGPT може не тільки звертатися до LLM, а й організовувати використання інструментів: працювати з файлами, виконувати код, шукати інформацію в Інтернеті, звертатися до зовнішніх сервісів, а результати знову передавати LLM через контекст.

Тобто спрощено я тепер бачу це приблизно так:

```text
                    ┌── історія
                    ├── пам'ять
                    ├── файли
                    ├── інструменти
                    ↓
користувач → ChatGPT → контекст → LLM
                ↑                 ↓
                └──── результат ──┘
```

І от тут я фактично підійшов до агентів. Бо якщо навколо LLM вже є програма, яка керує контекстом, дає їй інструменти і організовує їх використання, то виникає цілком логічне питання: а чим усе це принципово відрізняється від ШІ-агента?

## 3. Що таке програмний агент

У широкому сенсі програмний агент — це програмна сутність, яка діє у певному середовищі від імені користувача або іншої системи і має певну самостійність у виборі своїх дій. Основні властивості агентів:

- автономність;
- наявність мети або поставленої задачі;
- взаємодія із середовищем;
- реакція на зміни середовища;
- можливість самостійно вибирати наступні дії;
- збереження стану;
- можливість взаємодії з іншими агентами.

Загальна схема:

```text
середовище → сприйняття → рішення → дія → новий стан → ...
```

Саме поняття програмного агента з'явилося задовго до сучасних LLM та ШІ-агентів. Причому з агентами ми давно стикаємося, просто зазвичай не задумуємося над цим у таких термінах. Наприклад, агентом може бути: 

- програма, яка працює на комп'ютері у фоні, стежить за його станом і самостійно реагує на певні події; 
- бот, який отримує повідомлення і виконує відповідні дії; 
- ігровий персонаж, який сам реагує на зміни ігрового середовища; 
- програма моніторингу, яка збирає стан системи та передає його іншій системі.

З конкретних давно відомих прикладів — SNMP Agent, Zabbix Agent, Jenkins Agent/Node, GitLab Runner, агенти систем резервного копіювання та моніторингу. 

Тут для мене важливіше не конкретна назва програми, а сам принцип:

```text
агент ≠ обов'язково ШІ
```

Тобто LLM не створила поняття агента. Вона дала програмному агенту значно складніший механізм прийняття рішень. І вже звідси можна переходити до питання, що ж тоді змінилося з появою ШІ-агентів.

## 4. Що таке ШІ-агент

Тепер можна повернути ШІ до загального означення агента. ШІ-агент — це програмний агент, який використовує ШІ для прийняття рішень. У сучасних агентних системах у цій ролі найчастіше використовується LLM.

Умовно:

```text
ШІ-агент = агентна програма + LLM + інструменти + середовище + контекст/стан
```

Тут для мене важливим було розділити:

```text
агент ≠ LLM
```

LLM вирішує, що доцільно робити далі, але сама по собі не ходить по файловій системі, не запускає програму і не змінює файли. Агентна програма організовує цей процес: формує контекст для LLM, викликає потрібні інструменти, отримує результати, змінює стан і за потреби знову звертається до LLM.

Тобто виходить цикл:

```text
стан середовища
      ↓
    контекст
      ↓
     LLM
      ↓
рішення про наступну дію
      ↓
  інструмент
      ↓
зміна середовища / результат
      ↓
новий контекст
      ↓
     LLM
      ↓
     ...
```

## 5. А чим тоді це відрізняється від ChatGPT?

Оце питання в мене якраз виникло після попереднього розбору. Бо ChatGPT теж має LLM, керує контекстом і може використовувати інструменти. Тобто межа вже не виглядає такою очевидною.

У звичайному діалозі значну частину циклу організовую я сам:

```text
я ставлю задачу
      ↓
   ChatGPT
      ↓
отримую відповідь
      ↓
щось роблю / перевіряю
      ↓
результат знову передаю ChatGPT
      ↓
отримую наступну дію
      ↓
     ...
```

Наприклад, ChatGPT каже мені виконати команду на Raspberry Pi. Я сам заходжу через SSH, виконую її, копіюю результат назад і питаю, що робити далі.

В агентній системі значну частину цього циклу бере на себе сама програма:

```text
мета → LLM → дія → результат → LLM → наступна дія → ... → результат
```

Агент може сам прочитати файл, виконати команду, отримати помилку, вирішити, що треба змінити, відредагувати файл, запустити тест і перевірити результат. Користувачу не обов'язково бути посередником на кожному кроці.

Тому різниця для мене тут не стільки в наявності LLM чи інструментів — вони є і в ChatGPT, — скільки в ступені автономності та в тому, **хто організовує цикл «оцінити стан → вирішити → виконати → перевірити результат → вирішити, що робити далі».**

## 6. Середовище агента

Середовище — принципова частина агентної системи. Це той зовнішній світ, з якого агент може отримувати інформацію і на який може впливати за допомогою своїх інструментів.

Для coding-агента середовищем може бути:

```text
файли проєкту + Git + ОС + встановлені програми + бібліотеки + зовнішні сервіси
```

А `terminal`, робота з файлами, Git-команди тощо — це вже інструменти, через які агент взаємодіє з цим середовищем.

Цікаво, що саме середовище може використовуватися і як своєрідна довготривала пам'ять агента. Наприклад:

```text
AGENTS.md
README.md
код
конфігурації
Git history
журнали
```

Агент може залишити там інформацію і використати її при наступній роботі. Але тут діє той самий принцип, який ми вже розібрали для ChatGPT:

```text
інформація є в середовищі ≠ інформація є в контексті LLM
```

Щоб LLM могла використати вміст `AGENTS.md`, код або журнал, агент спочатку повинен отримати цю інформацію із середовища і додати потрібну її частину до контексту.

## 7. Codex

Тепер Codex для мене вже простіше розкласти на складові. Це сучасна агентна система, спеціалізована на роботі з програмним кодом.

Спрощено:

```text
Codex
├─ LLM
├─ агентна логіка
├─ керування контекстом і станом
├─ інструменти
└─ середовище
```

Я ставлю Codex не окремі команди, а задачу. Наприклад: знайти причину помилки і виправити її. Далі він може сам організувати цикл:

```text
прочитати код
      ↓
знайти потрібні файли
      ↓
запустити програму
      ↓
отримати помилку
      ↓
проаналізувати її за допомогою LLM
      ↓
змінити код
      ↓
запустити тест
      ↓
перевірити результат
      ↓
за потреби повторити цикл
```

Тобто Codex добре показує різницю між просто «поспілкуватися з LLM про код» і дати агенту задачу, яку він може сам виконувати у своєму середовищі.

Єдине, що я б ще додав після Codex, — короткий підпункт про `AGENTS.md` і skills. Ми це досить детально з'ясовували, і воно дуже добре показує на практиці, як агенту задають спеціалізацію та правила роботи без перенавчання самої LLM.

## 8. Кілька агентів

Одна система може запускати кілька агентів.

Причини:

```
паралельність + спеціалізація
```

Наприклад:

`агент 1 → архітектура`
`агент 2 → реалізація`
`агент 3 → тестування`

При цьому це не обов'язково різний програмний код або різні LLM. Це можуть бути кілька екземплярів тієї самої агентної програми і тієї самої LLM, але з різними:

```
ролями + інструкціями + контекстом + інструментами + задачами
```

Якщо звести всю нашу розмову до однієї формули:

**LLM генерує рішення, агент організовує цикл прийняття та виконання цих рішень, а середовище є світом, з яким цей агент взаємодіє.**
